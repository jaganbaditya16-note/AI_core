# Database and multi-tenancy (Phase 1)

Phase 1 adds the PostgreSQL foundation and the tenant boundary that every later
phase builds on. It adds **one** table. Agents, models, tools, data sources,
policies, events and incidents do not exist yet — what exists is the set of
conventions and the isolation mechanism they will inherit.

## The tenant model

An **organization is the tenant**. It is the single table that is not
tenant-owned, because it *defines* the boundary rather than living inside it.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | primary key, `gen_random_uuid()` server default |
| `name` | `varchar(200)` | trimmed, 1–200 characters (CHECK) |
| `slug` | `varchar(63)` | unique, `^[a-z0-9]+(-[a-z0-9]+)*$` (CHECK) |
| `status` | `varchar(32)` | `active` \| `suspended` \| `archived`, default `active` |
| `created_at`, `updated_at` | `timestamptz` | `now()` server default; `updated_at` refreshed on update |

Identifiers are generated by the database, so a client can neither choose nor
predict one. `status` is a `varchar` + `CHECK` rather than a PostgreSQL `ENUM`:
adding a state is then an ordinary migration instead of an `ALTER TYPE` that
cannot run in the same transaction that consumes the new value.

### Conventions every table inherits

Defined in `apps/api/src/aicore_api/db/base.py` and mixed into models, so they
cannot be forgotten:

- `UUIDPrimaryKeyMixin` — UUID primary key, server-generated.
- `TimestampMixin` — `created_at` / `updated_at`, timezone-aware.
- `TenantOwnedMixin` — `organization_id uuid NOT NULL` referencing
  `aicore.organizations(id)` **ON DELETE RESTRICT**, indexed.

`ON DELETE RESTRICT` means deleting a tenant can never cascade into, or orphan,
its data. Removing a tenant is an explicit operational procedure.

Constraint names are deterministic (`pk_/fk_/uq_/ix_/ck_` naming convention), so
a migration can be read and reversed without guessing. A constraint given an
explicit name *overrides* that convention — which is why a drift test compares
the names the models render with the names in the database.

## Tenant isolation

Three layers, described here in the order they act:

1. **Declaration.** A table is tenant-owned exactly when it carries an
   `organization_id` column via `TenantOwnedMixin`. Nothing maintains a list, so
   nothing can fall out of date.

2. **The guard** (`db/tenancy.py`). A SQLAlchemy `before_execute` hook on the
   **`Engine` class** inspects every statement before it reaches PostgreSQL:

   - a statement touching a tenant-owned table with **no tenant bound** is
     refused (`TenantScopeError`);
   - a statement touching a tenant-owned table that **does not filter on
     `organization_id`** is refused as well — "forgot the `WHERE` clause" is a
     loud error, not a cross-tenant read;
   - `SELECT`, `INSERT`, `UPDATE`, `DELETE` and raw `text()` SQL are all covered.
     ORM selects are matched through `get_final_froms()`, raw SQL by matching the
     tenant-owned table names in its text (stricter than parsing it).

   **DDL is deliberately exempt**: `CREATE`/`ALTER`/`DROP` are schema management
   performed by reviewed migrations, which necessarily run with no tenant in
   scope. Protecting that boundary would break Alembic rather than secure data.

3. **The data layer** (`db/repositories/`). `OrganizationScopedRepository`
   resolves the tenant from an explicit argument or the bound context, and fails
   closed if neither exists — so a query for tenant-owned data cannot be built
   without one. `_scoped(model)` always carries the tenant predicate, and
   `execute(statement)` binds the tenant around execution, which is what the
   guard checks.

Tenant context is explicit and request-scoped: a `ContextVar` set by
`bind_tenant(...)` / `tenant_scoped(...)` and reset in a `finally` block, so one
request's tenant cannot leak into the next task. There is no ambient default
tenant — omitting it is a hard failure, never a silent fallback.

### What this does *not* protect against

- A compromised process: it holds the same database credentials the guard uses.
  This is an application-level boundary, not a defence against a hostile client.
- A semantically wrong filter: the guard checks that `organization_id` is
  mentioned, not that the predicate is correct. Row-level correctness is what
  Row Level Security would add.

### PostgreSQL Row Level Security: design, not yet enabled

RLS is **not** enabled in Phase 1, deliberately: policies are database objects
that must be migrated, tested and operated (they need a role strategy and a
migration path), and the current phases run as a single application role where a
policy would add complexity without adding enforcement.

What Phase 1 does is make RLS a drop-in later. `tenant_scoped(connection, org)`
already pushes the tenant into the transaction with
`set_config('aicore.organization_id', ..., is_local => true)`, transaction-local
so it cannot outlive the work. Enabling RLS then means one migration adding:

```sql
ALTER TABLE aicore.<table> ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON aicore.<table>
  USING (organization_id = current_setting('aicore.organization_id', true)::uuid);
```

No call site changes. Until then, `alembic check` and the isolation tests are
what keep the boundary honest.

## Migrations

Alembic, as a **dev dependency** (`apps/api/pyproject.toml`). The API runtime
image installs only runtime dependencies — schema changes are applied from the
repository, not baked into the application image.

```
alembic.ini                     # no URL in it: credentials come from the environment
database/migrations/env.py      # reads AICORE_DATABASE_URL through the app's settings
database/migrations/versions/
  0001_organizations.py         # Phase 1: schema + tenant root
```

```bash
bash scripts/migrate.sh upgrade head      # apply
bash scripts/migrate.sh check             # fail if models and schema disagree
bash scripts/migrate.sh downgrade -1      # reverse
```

Two traps worth knowing, both of which produced a *silent* no-op during
development and are now covered by tests:

- Alembic treats a transaction that is already open as externally managed and
  never commits it. `env.py` therefore creates the `aicore` schema in its own
  committed transaction (`engine.begin()`) before migrations run; issuing that
  statement on the migration connection would make every migration disappear
  without an error.
- `script_location` and `prepend_sys_path` use `%(here)s`, so migrations work
  from any working directory.

Rules: one concern per revision, every revision states its downgrade, no
unreviewed `--autogenerate` output, credentials never written into `alembic.ini`
or a revision file.

## Verification

```bash
bash scripts/test-db.sh     # real PostgreSQL: migrate from scratch, drift check,
                            # readiness, and the whole test suite
```

`apps/api/tests/` covers the boundary rather than the plumbing:

| File | What it proves |
|---|---|
| `test_tenant_isolation.py` | unscoped and unfiltered statements are refused; a tenant-scoped repository cannot be built without a tenant; tenant A cannot read tenant B's rows; unknown tenants are rejected by the foreign key |
| `test_organizations.py` | persistence, uniqueness, defaults, CHECK constraints, `ON DELETE RESTRICT`, no tenant data in `repr` |
| `test_migrations.py` | revision head, downgrade present, models match the migrated schema, constraint names match, no extra tables |
| `test_organizations_api.py` | the minimal HTTP persistence path, and that it is absent outside development/test |

`tests/tenant_fixture.py` declares a **test-only** tenant-owned table. Phase 1
ships no domain table, so there would otherwise be nothing to test the boundary
with; the fixture inherits the real mixin and lives on its own metadata, so it
can never appear in a migration or in production.
