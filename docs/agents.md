# The agent registry (Phase 4)

Phase 4 answers one question the inventory cannot:

> Which agent is this, and is it the same agent it was last week?

Phase 3 records that an organization *has* an agent: a name, a type, an owner, a
lifecycle state. Phase 4 gives that record a **stable identity** — a value the
server generates, that survives a rename and a version bump, and that later phases
can attribute actions to. It also records what kind of agent it is, which version
is registered and where it runs.

It is the **IDENTIFY** pillar, and like Phase 3 it is honest about its edges: the
registry *identifies* agents. It does not run them, restrict them, contain them or
watch them.

## What this phase is, and what it is not

**It is** a per-organization agent registry: one record per agent, an identity the
server issues and never derives from anything a client sends, a closed category
vocabulary, version metadata, a validated lifecycle, an owner who is a member of
the same organization, and an API to register, read, change and remove agents.

**It is not** agent execution or control. There is no runtime, no session, no tool
invocation, no permission grant to an agent, no interception and no kill switch.
(Phase 6's policies and Phase 7's action firewall constrain what a *member* may ask
this system to run; neither of them reaches into an agent or constrains what an agent
does.) Specifically:

- `status: suspended` is a **recorded state**. It does not stop an agent, revoke a
  credential, block a tool or interrupt a session — nothing in this build does any
  of those things, and the API offers no endpoint that claims to.
- A category (`security`, `autonomous`, …) **describes**; it never **grants**. No
  permission in this build is derived from a category.
- There is no `agent.execute`, `agent.suspend`, `agent.approve`, `agent.control` or
  `agent.policy.*` permission. A permission for something that cannot happen would
  be a claim, not a control.

## Identity: what it is, and what it is not

Every registered agent has an `identity_id`: a UUID generated by PostgreSQL
(`gen_random_uuid()`), never by the application and never from request input.

| Property | Why it matters |
| --- | --- |
| Server-generated | A client cannot choose, guess or replay an identity — there is no request field for it |
| Stable | Renaming an agent, changing its version, its category, its owner or its lifecycle state leaves `identity_id` untouched |
| Unique per organization | A per-tenant lookup can never be ambiguous; two tenants may hold the same identifier value without either learning anything about the other |
| Not derived from the name | Two teams with a "Support Triage" are two agents, and neither rename rewrites the other's history |

**The display name is never the identity.** `display_name` is a label a human
reads, and it is mutable by design — it appears in the API as `display_name`
precisely so that it is not mistaken for the identifier a later phase will store.
Later phases (approvals, action authorization, audit) refer to `identity_id`, and
that value never changes.

`id` — the registry row's primary key — is also returned, and is *not* the
recommended identifier to persist. It is stable too, but it is an implementation
detail of this table, while `identity_id` is the concept.

## The relationship to the inventory

An agent is the specialized form of the Phase 3 `agent` asset. There is one
inventory and one registry, linked one-to-one:

```
aicore.assets (asset_type = 'agent')          aicore.agents
├── name / description          ◄── display name, description
├── status / environment        ◄── lifecycle state, deployment environment
├── owner_membership_id         ◄── who is accountable
└── id ─────────────────────────┐
                                └──► asset_id  (UNIQUE: one identity per agent)
                                     identity_id (UNIQUE per organization)
                                     category / version / framework / build_revision
                                     identity_metadata (runtime, region, instance)
```

Three decisions live in that picture.

**The registry does not duplicate the inventory.** An agent's name, description,
lifecycle, environment and owner are stored once, on the asset, where Phase 3
already constrains them — including the composite foreign key that makes a
cross-tenant owner unrepresentable. A second copy in `agents` would be a second
thing to keep in sync, and the registry's job is identity, not a shadow inventory.

**One identity per asset, enforced by the database.** `agents.asset_id` is unique,
so two registry records cannot claim the same agent. `(organization_id, asset_id)`
references `assets(organization_id, id)`, so a registry record cannot point at
another organization's asset even if application code forgot to check — the same
composite-key technique Phase 3 uses for owners.

**Deleting the record deletes the identity.** The reference cascades, so an
identity whose agent no longer exists in the inventory is not a state the database
can reach. `DELETE /agents/{agent_id}` removes both, in one transaction, and emits
both events.

## Lifecycle

Four states, and a transition table that is enforced in one place
(`aicore_api/core/agents.py`) so every write path — this API today, an
administrative or ingestion path later — obeys the same rules:

```
draft ──► active ──► suspended ──► active
  │         │            │
  │         └────────────┴──────► retired   (terminal)
  └─────────────────────────────► retired
```

| From | Allowed |
| --- | --- |
| `draft` | `active`, `retired` |
| `active` | `suspended`, `retired` |
| `suspended` | `active`, `retired` |
| `retired` | — (terminal) |

A registration may start an agent in `draft` or `active`, and only those two: an
agent is not *born* suspended or retired, so a request that says otherwise is a
`422`. Moving to a state the table does not allow is a `409` — the request was
well-formed and the record says no — and `retired` is final: a retired agent does
not silently return to service. Moving to the state an agent is already in is a
no-op, so a repeated `PATCH` stays idempotent.

## Categories

A closed vocabulary of eight:

| Category | What it covers |
| --- | --- |
| `assistant` | A conversational assistant |
| `workflow` | A step-wise automation over known inputs |
| `autonomous` | An agent that decides its own next actions |
| `coding` | Software engineering assistance |
| `customer_support` | Customer-facing support |
| `data` | Data extraction, transformation or analysis |
| `security` | Security operations |
| `other` | Everything that does not fit, on purpose |

Like the inventory's `asset_type`, adding a category is a deliberate change: a
value in the vocabulary, a migration for the check constraint, and a mirror in
`packages/types`.

## Version metadata

An agent identity outlives the versions of the agent. Registered once at `1.2.0`,
moved to `1.3.0`, the identity is the same — that is the entire point of separating
the two.

| Field | Meaning |
| --- | --- |
| `version` | The version label being registered. Required, ≤ 64 characters. Not SemVer-validated: `1.2`, `2026-04-18` and `0.1.0-rc1` are all real versions and all accepted |
| `build_revision` | Optional, ≤ 128 characters: which build of that version. Its meaning is the organization's convention |
| `framework` | Optional, ≤ 64 characters: what it is built on (`langgraph`, `openai-agents`, …) |

This is not version *management*: there is no deployment, no rollout, no artifact
registry. A version is a field that changes on `PATCH`, and the change is recorded
in the update.

## Runtime identity foundation

A later phase needs to answer "who is acting?" for three kinds of actor, and Phase
4 provides the third one's identifier without inventing a second authentication
system:

| Actor | Identified by | Where |
| --- | --- | --- |
| A human | `user_id`, via a membership | Phase 2 (`/me`, memberships, roles) |
| A human through an application | the same human's credential | Phase 2, deliberately unchanged |
| An **AI agent** | `identity_id` | Phase 4, this table |

An agent identity is an **identifier, not a credential**. It cannot be presented
for authentication, it grants nothing, and it is safe to read through the API. The
registry stores no secret: `identity_metadata` is a closed model (`runtime`,
`region`, `instance`), unknown keys are refused, and a key whose name looks like a
credential (`api_key`, `token`, `secret`, `password`, `private_key`, …) is refused
outright — asserted by tests, in the database and through the API.

## Ownership

Every agent belongs to exactly one organization, and has at most one owner:

- `organization_id` comes from the URL path and the caller's membership — never
  from a request body;
- `owner_user_id` in a request is resolved to a membership **of that organization**;
  a user who is not a member, or whose membership is not active, is a `422`;
- the owner is stored as `assets.owner_membership_id`, which is a *composite*
  foreign key to `memberships(organization_id, id)` with `ON DELETE RESTRICT`.

The last point is the important one: "an agent in organization A owned by a member
of organization B" is not a row PostgreSQL will accept, whatever the application
does. Removing a member who still owns records is refused rather than cascaded.
Re-registering an agent **never** reassigns its owner: a registration fills an
empty owner slot, and a request that contradicts a recorded owner, name,
environment or lifecycle state is a `409` instead of a silent write.

## The API

Six routes, all under `/organizations/{organization_id}`, all requiring an API
token and a permission:

| Route | Permission |
| --- | --- |
| `GET /agents` | `agent.read` |
| `POST /agents` | `agent.create` |
| `GET /agents/identity/{identity_id}` | `agent.read` |
| `GET /agents/{agent_id}` | `agent.read` |
| `PATCH /agents/{agent_id}` | `agent.update` |
| `DELETE /agents/{agent_id}` | `agent.delete` |

Registering:

```bash
curl -s -X POST "http://localhost:8000/organizations/$ORG/agents" \
  -H "Authorization: Bearer $AICORE_TOKEN" -H 'Content-Type: application/json' \
  -d '{"display_name": "Claims Triage",
       "category": "customer_support",
       "version": "1.2.0",
       "environment": "production",
       "owner_user_id": "<user-uuid>",
       "framework": "langgraph",
       "identity_metadata": {"runtime": "python3.11", "region": "ap-south-1"}}'
```

The response carries the identity the server generated:

```json
{
  "id": "6f0f5b1e-…", "organization_id": "…", "asset_id": "…",
  "identity_id": "8f48dc42-…",
  "display_name": "Claims Triage", "category": "customer_support",
  "version": "1.2.0", "framework": "langgraph", "build_revision": null,
  "status": "draft", "environment": "production",
  "identity_metadata": {"runtime": "python3.11", "region": "ap-south-1"},
  "owner": {"membership_id": "…", "user_id": "…", "email": "…", "full_name": "…"},
  "created_at": "…", "updated_at": "…"
}
```

Listing:

```bash
curl -s "http://localhost:8000/organizations/$ORG/agents?category=coding&status=active&total=true" \
  -H "Authorization: Bearer $AICORE_TOKEN"
```

Filters — `category`, `status`, `environment`, `owner_membership_id` — are
repeatable and are **ORed within one parameter, ANDed across parameters**. Category
is a registry column; status, environment and owner filter the agent's inventory
record, because the registry keeps no second copy of them.

| Parameter | Default | Limits |
| --- | --- | --- |
| `limit` | `50` | `1`–`200` |
| `offset` | `0` | `0`–`100000` |
| `total` | off | Adds the filtered count, so listing stays one query |

Items are ordered newest-registration-first by `created_at`, `id`, so pages do not
overlap.

Looking an agent up by identity — the operation a later phase performs when it has
to attribute something to an agent and must not trust a display name:

```bash
curl -s "http://localhost:8000/organizations/$ORG/agents/identity/$IDENTITY_ID" \
  -H "Authorization: Bearer $AICORE_TOKEN"
```

Changing an agent:

```bash
curl -s -X PATCH "http://localhost:8000/organizations/$ORG/agents/$AGENT_ID" \
  -H "Authorization: Bearer $AICORE_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version": "1.3.0", "status": "active"}'
```

`PATCH` is field-set-aware: an omitted field is unchanged, and `null` clears a
nullable one (`framework`, `build_revision`, `identity_metadata`, the owner, the
description). `identity_id`, `asset_id`, `organization_id`, `id`, `created_at` and
`updated_at` are not client-settable and are refused if sent.

Refusals follow the existing contract — `{"error": {"code", "message", "details",
"request_id"}}` — with, in particular: `401` without a usable token, `403` when the
role lacks the permission or the membership is suspended, `404` for an agent that
does not exist **or belongs to another organization**, `409` for a duplicate
registration, a contradiction with an existing record, or a lifecycle move the
transition table forbids, and `422` for anything the schema refuses. A foreign
agent, a foreign identity and an invented identifier produce byte-identical
`404`s, because a difference would be an enumeration oracle.

## Authorization

Four permissions, and no others:

| Permission | owner | admin | security_admin | ai_admin | analyst | viewer |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| `agent.read` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `agent.create` | ✅ | ✅ | — | ✅ | — | — |
| `agent.update` | ✅ | ✅ | ✅ | ✅ | — | — |
| `agent.delete` | ✅ | ✅ | — | — | — | — |

Read is deliberately broad — every role that can see an organization's inventory
can see its agents — while registering is stewardship (`ai_admin`, `admin`,
`owner`), lifecycle changes are supervision (`security_admin` and up, because
recording that an agent should be suspended is part of security work), and
**deleting an identity** is an administrative decision (`admin`, `owner` only).
`ai_admin` stewards agents without being able to erase them.

Every route declares its permission through `require_permission`, and a test reads
the requirement off the built application, so a route cannot quietly lose or change
its permission in a refactor.

## Tenant isolation

An organization can see its own agents and nothing else:

- the repository cannot be constructed without an organization, and every statement
  it builds is filtered to it; the engine-level guard in `db/tenancy.py` refuses any
  statement against a tenant-owned table that is not filtered on `organization_id`,
  including raw SQL;
- `GET`, `PATCH`, `DELETE` and the identity lookup answer `404` — the same status,
  body and headers — for an agent that belongs to another organization and for one
  that does not exist;
- naming another organization in the path does not resolve: the path is matched
  against the caller's own memberships, so the request fails before reaching the
  registry;
- an owner from another organization is not representable, and a user id that
  resolves to no membership here is a `422` rather than an assignment;
- the database refuses a registry row whose `organization_id` and `asset_id` name
  different tenants, and refuses two identities for one asset.

## Audit readiness

Registration, update and deletion emit domain events
(`agent.registered`, `agent.updated`, `agent.deleted`, plus `asset.created` /
`asset.deleted` when the registration also created or removed the inventory
record). This is the same seam Phase 3 established: a place a later audit phase
attaches to, not an audit system. There is no history table — an update overwrites
the previous value.

## What Phase 4 deliberately does not implement

Stated plainly, because a registry that overstates itself is worse than a small one:

- **No execution and no runtime control.** Nothing starts, stops, suspends,
  contains or interrupts an agent. `status` is a record.
- **No permission engine, no policy engine, no approvals, no kill switch, no
  monitor, no anomaly detection.** Those are other phases' work, and no endpoint,
  permission or type in this build pretends otherwise. Phase 7 added an action
  firewall, and the distinction it draws is the registry's own line: `/actions/execute`
  runs an *action* from a closed catalogue (one read-only assessment today), and
  nothing anywhere executes, starts, stops, contains or interrupts an *agent* — see
  [actions.md](actions.md).
- **No tool or model invocation, and no dependency graph.** Agents do not reference
  each other, tools or models.
- **No authentication for agents.** An identity is an identifier, not a credential;
  there is no agent login, no token issued to an agent and no second authentication
  system alongside Phase 2's.
- **No credential storage of any kind.** Not even hashed: the registry stores no
  secret material, so there is nothing to leak.
- **No history.** A version change or a lifecycle change overwrites the previous
  value; the event seam exists, the audit trail does not.
- **No bulk operations.** One agent per request.
- **No dashboard.** The registry is an API; the only client-side artifact in this
  phase is the shared TypeScript contract in `packages/types`.
